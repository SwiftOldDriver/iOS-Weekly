### 🐕 [读着有道理，已经说明不了什么](https://yousali.com/posts/20261102-ai-slop-attention/)
[@AidenRao](https://weibo.com/AidenRao)：面对大量 AI 内容，我们该如何决定什么值得读、什么值得信？作者从一次阅读经验切入：一篇文章用 Gall 定律(能运行的复杂系统，都是从能运行的简单系统长出来的)解释为什么照搬成熟团队的最佳实践常常失败，观点读起来很顺，但同一现象也可能有其他解释。这促使他重新审视自己的筛选习惯：账号涉猎广不一定意味着缺乏积累，具体的“踩坑经历”也可能被 AI 编造；即使一个人的判断得到过现实反馈，其可信范围也有限。

作者将新的筛选方法归纳为三个问题：内容是否与手头的问题相关，能否通过公开代码、产品或数据核对，以及对原因的解释是否考虑了其他可能性。在此基础上，他计划控制关注数量、延后追踪热点，并用 30 天实验检查阅读时间、实际行动和重要信息遗漏情况。文末还介绍了自己筛选关注名单的过程与局限。文章中的时间和数量阈值只是作者为个人实验设定的起点；这项实验也无法证明自己相信错误信息的概率会降低。

### 🐕 [Cognitive Debt: Keeping Your Codebase Understandable in the Age of AI](https://livsycode.com/best-practices/cognitive-debt-keeping-your-codebase-understandable-in-the-age-of-ai)

[@阿权](https://github.com/bqlin)：都 2026 年了，想必大家团队 AI Coding 都如火如荼了吧，文章提到了认知债务（Cognitive Debt）的观点，即对代码的实际行为缺少足够的理解，以致于后续维护、迭代要付出额外成本。AI Coding 可能能解决技术债务，但势必会放大认知债务的问题。

文章提出了以下一些观点，值得我们深思：

1. AI 能高速产出代码，但不能代替人建立对系统的心智模型。认知债务不是 AI 独有的，但是 AI 会加速它的积累。
2. 编译成功、测试通过是指第一步，不等于原物逻辑安全正确。AI 生成的实现和测试存在一起犯错的风险。
3. 重构目标是让业务链路更容易被**人**读懂。抽象本身无罪，但需警惕 AI 生成大量为抽象而抽象的间接层、泛化。
4. 文档不必长篇大论，关键流程记录业务不变约束即可，文档最大的危害是过期误导。
5. 团队要有脱离 AI 工具的排查能力；关键业务知识不能只保存在 AI 输出或者某一个人的脑子里。
6. 人工投入成本要和风险匹配：高风险模块多人工投入，普通模块适度即可，不要盲目大规模重构整个代码库。

最后可以总结为：AI 可以用来查找、生成草稿，但是人必须对代码行为拥有真实的理解，承担全部责任。

### 🐕 [Everyone’s got a quick question](https://uxdesign.cc/everyones-got-a-quick-question-374a736ff7cb)

[@zhangferry](https://zhangferry.com)：Bill Guo 回看了一个 15 人设计团队两年半的 2,413 条请求。53% 的问题已有答案，只是散在文档、Figma 和旧讨论里。他们做了一个叫 le goat 的 Agent，在 Slack 试用两周收到 228 个问题，后来也接入了 Figma 评论。据作者统计，日常找负责人的问题从每个工作日 6.3 条降到 1.8 条，首次回复的中位等待时间从 29 分钟降到 45 秒。 [作者互动版](https://le-goat.netlify.app/)

一次有人问表单标签的字号，Agent 查到 Notion 写待定、Figma 写 13px，代码却是 14px。团队早就定了 13px，文档没跟上，代码又在重构时改了。于是团队让 Agent 每周找这类冲突，附上当初的决定和修改草稿，请负责人审核。这套做法也能用在代码库里。README、接口文档和实现对不上时，可以先让 Agent 把冲突和相关提交列出来，再由维护者确认哪个才是当前约定。

### 🐎 [Cupertino 1.5.0: Five Months of Apple Documentation, Diffed](https://aleahim.com/blog/cupertino-v1-5-0-five-months-diffed)

[@Barney](https://github.com/BarneyZhaoooo)：文章复盘了开源离线 Apple 文档 MCP 工具 `Cupertino` 在 5 个月跨度内的版本 Diff，通过按页面地址对齐 39 万余页快照，展示了语料库重构的收益与回归排查：

- **结构化入库与校验流水线**：126,695 个旧页从网页抓取改为解析 Apple 结构化数据，补齐声明、`kind` 与平台版本字段，显著提升过滤检索能力；同时补充了 WWDC 字幕库及 `cupertino-rel refresh` 自动校验发布链路。
- **新增文档与折叠屏信号**：新增 27,494 页（零页丢失），七成落在底层系统框架，且在 SwiftUI / UIKit / XCUIAutomation 中浮现约 180 页 `iPhone Duo` 折叠屏文档（含 `ArrangementView`、`DeviceHinge`、`XCUIHinge` 等）。
- **回归缺陷与验证边界**：结构化转换引入了回归，正文残留原始 `doc://` 引用的页面增至 59,360 页，仍有 13.5% 页面缺少 `kind`；此外，旧正文行保留不足一半的 7.5 万页仅抽查了 7 页，且 Diff 脚本尚在仓库外，参考数据时需保留这一前提。

适合正在构建本地技术文档索引、Agent 离线知识库或关注语料质量回归的同学参考。

### 🐕 [Long-Running Agents: How to Keep Autonomous Work Reliable](https://livsycode.com/best-practices/long-running-agents-how-to-keep-autonomous-work-reliable/)

[@AidenRao](https://weibo.com/AidenRao)：让 Agent 持续执行数小时的工程任务，需要处理上下文丢失、执行中断、重复操作和结果验收等问题。文章以一个假设的 iOS 增量构建优化任务为例，介绍如何通过外层控制器分步启动会话、独立验证结果，并约束时间、成本和重试次数。作者详细区分了检查点与事件日志的职责，前者保存代码版本、工作区、产物和下一步，后者记录操作的执行过程，帮助恢复后的 Agent 核对实际状态。对于已经提交、却因断线而无法确认结果的远程任务，应先查询原任务，再依据服务端的幂等机制决定是否重试。构建优化部分还讨论了缓存与环境噪声、重复测量，以及代码生成脚本跳过执行后的正确性检查。全文给出了一套可恢复、可审查的长任务设计思路，适合正在将构建优化、CI 迁移和依赖升级交给 Agent 执行的开发者阅读。

### 🐎 [iOS 27 has some weird Dynamic Island behavior](https://christianselig.com/2026/10/ios-27-dynamic-island-bug/)

[@JonyFang](https://github.com/jonyfang)：如果你的 Live Activity 只需在灵动岛显示一个图标，升级到 iOS 27 SDK 后，记得测一下横屏布局。按 Apple 文档的写法，图标放在 `compactLeading`，`compactTrailing` 返回 `EmptyView()`，系统会自动隐藏空的一侧。本文作者发现，常规宽度下显示正常，但在横屏等宽度受限的场景下，空视图仍会占位，把灵动岛撑高。

同一份代码用 iOS 26 SDK 构建时，系统在宽度受限时会选用 `minimal` 布局，跳过 `compactTrailing`。但升级 SDK 后会出现问题。作者已将问题反馈给 Apple，反馈编号为 `FB25301955`。如果你的 App 也用了这种单图标设计，升级 SDK 后可以顺手测一下横屏效果。

### 🐕 [Agent Evaluations: Measuring and Improving AI Agent Performance](https://livsycode.com/best-practices/agent-evaluations-measuring-and-improving-ai-agent-performance)

[@Cooper Chen](https://github.com/cjlcooper)：这篇文章将“代理评估”从抽象主张拉回工程团队的真实困惑：给编码代理加一项性能优化技能，它解释合理、构建通过，但你凭什么判断它真的变好了？文章以 SwiftUI 性能技能为切口，示范围绕明确决策问题设计评估——不看代理“说了什么”，而看它在定义任务、隔离环境和评分规则下，是否稳定交付可验证改动。想试这项技能，可以借文中的滚动卡顿任务做个小对照：让两套配置从同一提交的独立工作区开始，把功能测试和重复测量各自留档。示例里构建与行为测试都通过，但仪器数据波动太大，性能一栏仍填“无法判定”。如果还想看 agent 会不会自己发现技能，文中把这项和显式载入分开比较。它最有价值之处，是把评估还原为可重复动作：从真实缺陷选任务，在安全副本上运行，同时检查最终代码状态和代理轨迹，而非只读总结。如果你厌倦“感觉好像变好了”，这篇文章给了一个今天就能上手的起点。

### 🐎 [Why You Shouldn't Miss Antigravity app](https://wezzard.com/post/2026/11/making-antigravity-gui-usable-86d9)
[@老驴](https://weibo.com/u/6090610445)：最近 Google 模型明显变强，加上 GPT 防御性编程越来越严重，不少人开始从 Codex 转向 Gemini，尝试 Carbon、Neon 等新模型。但往往绕不开 Antigravity 这个 harness。之前觉得它桌面端弹窗烦、找不到全局 Skills 的，可以看看这篇：不仅讲清楚了怎么把 Generative UI、/btw 侧边只读问答和 iPad 原生远程控制用起来，还给了一些常见问题比如“开了 Auto 为什么还是弹权限”和“三端 Skills 目录割裂”的根因。照着改完双端 Turbo 和 skills.json，用起来顺手很多。

### 🐕 [Apple's Xcode Plugin for Claude Code: What It Installs](https://blakecrosley.com/blog/xcode-plugin-claude-code)
[@DylanYang](https://github.com/Dylan19Yang)：本文拆解了 Apple 上架 Claude Code 官方市场的 Xcode 插件的底层机制，该插件并无远端分发的文件包，而是通过执行本地 xcrun 命令由本机 Xcode 生成插件目录，内含 16 项覆盖 SwiftUI、测试、本地化、性能调优等方向的开发技能，以及 1 个提供 IDE 操作工具的 MCP 服务。文章还对比了其与手动配置 MCP 桥接的差异，讲解了安装权限规则、版本随 Xcode 迭代的特性与本地审查方法，给开发者提供了完整的接入评估参考。
